# Track & Field Career Game (Godot)

In-depth career mode track and field (yleisurheilu) game, built in Godot together with the user.

**Status:** M1 done — character creation, weekly training, season calendar, save/load, the 800m race simulation, season rankings and the responsive UI (desktop + phone portrait) are done. M2 part 1 (day-by-day mode, injuries & health; designed in GDD 4.5–4.7, steps in the roadmap): steps 1 (day engine + hooks), 2 (week strip, day editor, Today card, Report tab), 3 (health model, headless), 4 (health UI) and 5 (balance & playtest: soreness thresholds tuned, race-day "sore" bug fixed, numbers in GDD 4.6 "Tuned (step 5)") done; silent stress fractures decided and applied (option B3); next step 6 (season periodization), then the multi-year check, coaching and school. Youth opponents stay fictional (minors); real athletes only at senior level. Milestones: `docs/ROADMAP.md`.
**Design doc:** `docs/GDD.md` — the source of truth for all design decisions. Read it before design or code work.

**User:** no programming experience — explain how to run/test things in plain steps; Claude writes all code.

## Tech & structure
- Godot **4.7.2** (user's version), GDScript only, GL Compatibility renderer (PC + mobile). Base viewport 1280x720, stretch `canvas_items`/`expand`.
- `scenes/main.tscn` + `scripts/main.gd` — app shell; applies theme, hosts the current screen.
- Autoloads: `Data` (`scripts/core/data.gd`, loads `data/*.json`), `Router` (`scripts/core/router.gd`, `Router.go("screen_id")`; register screens in `SCREENS`), `Game` (`scripts/core/game.gd`, current athlete + today's date; career starts Mon 2 Nov 2026).
- `Athlete` (`scripts/core/athlete.gd`): attributes are floats 1–20 keyed by id from `data/attributes.json`; `to_dict`/`from_dict` for saving. `AthleteFactory` builds the 14-year-old from creation choices (base ranges + background answer effects from `data/background_questions.json` + 12 points, max +3 each).
- **Responsive UI:** `Layout` (`ui/layout.gd`) holds `Layout.compact` (true for a portrait/squarish window, i.e. phone). `main.gd` picks the mode on every window resize, sets the window `content_scale_size` (wide: 1280x720-based, scale floor 0.7; compact: 480 px logical width), rebuilds the theme (`ThemeBuilder.build(compact)`) and emits `Router.layout_changed`. Every screen builds its layout from `Layout.compact` and rebuilds on that signal (hub, wizard, race, load game, main menu). Rules: use `UIKit.flex()` (BoxContainer that is a row on PC, a column on phone), `Layout.page_margin()`, 44 px minimum for anything tappable, **no hover-only info** (use `UIKit.attr_row(..., description)` / `UIKit.tap_to_explain` and `ChoiceCard` instead of tooltips). Hub: tabs on top (`TabButton`) on PC, bottom bar (`BottomTabButton`) on phone. Race decisions are a full-screen dimmed overlay. Check with `tools/layout_check.gd` (live-resizes through 1280x720, 720x1280, 390x844, 1000x900, 844x390) and `screenshot_tour.gd --resolution 390x844`.
- **Backdrop:** `scripts/ui/backdrop.gd` + `ui/backdrop.gdshader` draw the background gradient; a photo in `assets/backgrounds/<screen_id>.jpg` (or `default.jpg`) is shown blurred and darkened (see the README there). Three CC BY-SA photos are included (Forss + Kuivisto at Kalevan Kisat 2018 by Tuomas Vitikainen, Lahti Stadium by Kallerna; credits in that README, still needs an in-game Credits screen). Their `.import` files must keep `mipmaps/generate=true` (the blur samples a mip level). Panels are slightly translucent (`Palette.SURFACE_PANEL`).
- Screens built in code use `UIKit` (`scripts/ui/ui_kit.gd`) helpers: labels, panels, toggles, FM-style `attr_row` with value colours.
- Screens: `scenes/screens/*.tscn` (mostly just a root node now) with scripts in `scripts/ui/`; the hub, wizard and race screen build their shell in code so it can switch layout.
- Theme is built in code: colours/sizes in `ui/palette.gd`, styles in `ui/theme_builder.gd`. Label variations: TitleLabel, HeadingLabel, MutedLabel, CaptionLabel; button variation: PrimaryButton. Font: Inter (`assets/fonts`, OFL).
- World data lives in `data/*.json` (events, attributes) — never hard-code real-world data in scripts.
- Verify changes before pushing: download Godot 4.7.2 Linux build to the scratchpad, run `godot --headless --import --path .` then `godot --headless --path . --quit-after 30` and check for errors; screenshots via `xvfb-run ... --rendering-driver opengl3 --write-movie out.png --fixed-fps 10 --quit-after 15`, or the click-through tour `xvfb-run -a godot --path . --rendering-driver opengl3 -s res://tools/screenshot_tour.gd -- <out_dir>` (update it when screens change). Look at the screenshots before pushing.
- `Training` (`scripts/core/training.gd`): session/fatigue/progression model (fatigue day by day, progression per week); `Training.simulate_week` plays a whole week in one go (balance tool, plan preview). Career hub has Overview / Training / Calendar / Rankings / Report tabs; header: today's date, **Next day** + **Play week** (phone: Day / Week), Save, Menu.
- **Day engine (GDD 4.5/4.7):** `Game.date` is *today* (the next day to play); `Game.week_monday()` for week-based code (training tab, plan preview). `Game.advance_day()` plays one day, `Game.advance_week()` plays to Sunday night; both (and `finish_race()`) return `Game.DAY_DONE` / `WEEK_DONE` / `RACE` (race screen, `race_day` set) / `STOP` (unanswered stop event). A race reached during Play week continues the week after `finish_race()`; via Next day it completes just that day. `WeekSim` (`scripts/core/week_sim.gd`) is the week in progress (`Game.current_week()`, made on demand, synced with `training_plan` and entries): `play_day()` / `race_done()` per day, `end_week()` applies progression (Sunday night) → `last_report`; then `Rivals.train_week`. Day changes for this week only: `set_sessions / swap_session / skip_session / add_session / make_rest_day / set_intensity / reset_day(d, ..., by)` with `by` in player / coach / injury; only unplayed non-race days; a change equal to the plan is dropped. Intensity multipliers (load, effect) in `data/health.json` (Normal = 1.0, so the M1 balance is bit-for-bit unchanged). Day loop slots: `GameSystem` (`scripts/core/game_system.gd`) hooks `on_day_start → (training/race) → on_health → on_day_end`, `on_week_end`, `on_answer`, own `to_dict/from_dict`; `Game.systems` = `HealthSystem` (see "Health model" below) + `DevEvents` (debug builds only: **T** in the hub arms a test stop event for the end of the next played day; not an F key, since F7/F8 pause/stop a game run from the editor). Events: `Game.post_event(source, title, text, choices, stop)` → `{id, date, source, title, text, choices, stop, answer}`; `pending_event()`, `answer_event()` → the source system's `on_answer`. A stop event at day start pauses before the day is played (`week.day_started`). `Game.day_log`: per played day `{date, day_type, sessions, intensity, race, load, fatigue, events}` plus whatever systems put in `ctx.log_extra` (health: `soreness`, `health`); log and answered events keep 28 days. The hub shows a pending stop event as a dimmed full-screen panel. Check with `tools/day_engine_check.gd` (optionally `-- <v1 save file>`).
- **Week strip & day editor UI (M2 step 2, UI only, the engine is unchanged):** the hub shows a `WeekStrip` (`scripts/ui/week_strip.gd`) under the header: 7 cells Mon–Sun of `Game.current_week()` (date, one marker per session coloured by intensity — `Palette.DAY_EASY/NORMAL/HARD` —, RACE badge, accent dot = changed, dimmed + fatigue dot when played, accent border = today, white border = open in the editor; PC also shows session names). Tapping a cell opens the `DayEditor` (`scripts/ui/day_editor.gd`): PC = side panel right of the tabs (`SIDE_PANEL_WIDTH`, narrower on a short window; Overview drops to 2 columns while it is open), phone = bottom sheet over a dimmed layer (tap the dim area or Close; height fitted to content, max 72 %). Three views: an editable day (session pickers with the reason in the name when not possible this month, Remove, Add session ≤ 2, Rest day, Easy/Normal/Hard with descriptions and multipliers from `data/health.json`, load for the day vs plan, "Changed by you", Back to plan = `WeekSim.reset_day`), a played day (read-only, from the day log), a race day (read-only; marked spots in the code for the coach Veto and for scratching). All edits go through the `WeekSim` day-change functions with `by = "player"`; the editor emits `changed` so the hub redraws the strip and the Today card. `DayInfo` (`scripts/ui/day_info.gd`) is the one read-only description of a day (`DayInfo.of(week, d)`) used by strip, editor, card and report. `TodayCard` (top of Overview; tap = today's editor; its health part, the soreness rows and injury blocks, is step 4: see "Health UI"), `ReportView` (Report tab: this week day by day from `Game.day_log`, then last week's report and its days). `career_hub.gd` keeps `_selected_day`, `_open_day / _close_day`, `_refresh_week_ui()` (header + strip + open editor; closes the editor when a new week starts). The tour and layout check cover all of it; `layout_check.gd` also prints `OVERFLOW` for any control wider than the window or its scroll area; `day_engine_check.gd` has a "UI models" section (planned load = played load, strip data identical after save/load).
- **Health model (GDD 4.6, M2 step 3, headless):** `HealthSystem` (`scripts/core/health_system.gd`, in `Game.systems`, id `health`). Data: `data/health.json` (body areas with daily `keep`, soreness levels 34/52/70 (step 5; they were 30/50/70, which left the coach plan "a bit sore" on 4 days out of 10), strain multipliers, spike = acute 7 d vs chronic 28 d impact, **adaptation** = capacity that follows the chronic load slowly, injury risk curve, acute, escalation, illness, detraining, plan risk, rival injuries, restriction presets), `data/injuries.json` (catalogue: tier niggle/injury/serious/illness, area, cause overuse/acute/illness, min_strain, weight, age/growth/female, phases `{restriction, bans, days, locked}`, escalates_to, race_slowdown), sessions in `data/training.json` (and `race_session` in competitions.json) have `strain` per area, `acute` chances, `tags` (run, hard, speed, plyo, long, drills, legs, ski, cross) and `instead` (swap list when banned); cross-training sessions aqua_jog / stationary_bike / swimming / gym_core. No injury numbers in scripts. Day loop: `on_day_start` re-applies the limits to this week's days ≥ today (and withdraws from a race when locked), `on_health` = strain + fade + capacity → escalation/phase progress → rolls (acute per session, overuse per area, illness) → diagnosis / "sore" stop events (`event.kind` = `diagnosis` / `sore`; when the next day is a race day the "sore" event has `meet` = its key and the choices race as planned / scratch, since a race day can't be made Easy or Rest) → limits; `on_week_end` = extra detraining after > 10 days without training, running-specific detraining after > 10 days without running (cross-training doesn't count) + rival injuries (`out_weeks` on the rival dicts; `Rivals.is_out`, skipped in `train_week` and `pick_field`); `on_week_start` (new `GameSystem` hook, called by `Game.current_week()` when a week is created) puts the limits into a new week before Monday. Limits are day changes `by = "injury"`, recomputed idempotently from the plan; `override_day(d)` = the player trains through (not when locked); training/racing through can escalate (shin splints → stress reaction → fracture). Own RNG (seed + state saved as strings), so save/load continues bit for bit; old saves load with an empty health state. **For the UI (used by the health UI, below):** `soreness()`, `soreness_info(area)` (causes + what helps), `active()` (name, phase, allowed, locked, days left, range, expected return), `ban_reason(session, d)`, `day_locked(d)`, `can_override/override_day(d)`, `can_race()`, `race_slowdown()` (applied in `RaceDay._player_entrant`, `RaceDay.slowdown`), `load_vs_normal(week)` %, `plan_risk(plan)` → low/moderate/high (`RISK_NAMES`), `proneness_hint()`, `refresh()` after editing the weekly plan; the day log gets `soreness` and `health` (via `ctx.log_extra`). `HealthSystem.model_enabled` (static) switches it all off: `day_engine_check`, the tour and the layout check run with it off (repeatable), `training_balance` part 2 proves the M1 fingerprints are identical with it off. Debug builds: **H** in the hub prints `debug_text()` (hidden numbers) to the Output panel. Tools: `tools/health_check.gd` (ALL CHECKS PASSED), `tools/health_season.gd -- [plan] [policy] [seed] [days]` prints one athlete's season day by day, `tools/training_balance.gd [-- n [rows|all [start age 14/15/16]]]` part 3 = 200 athletes per row (~2 min per row; run rows as separate processes in parallel, about 4 at a time; each row also prints boys vs girls, injuries by area, stops per year, days with sore areas, colds by month and the ability gain with its standard error; `Game.autosave = false` in tools that play thousands of days), `tools/season_playtest.gd -- <out_dir> [coach|hard] [careful|neutral] [seed] [days]` (a windowed run: plays a season through the real hub buttons, screenshots of the first of each stop event, timings of the hub and the autosave; add `--resolution 390x844` for the phone). **The check tools print "ALL CHECKS PASSED" even when a `SCRIPT ERROR` aborted one check function: always read stderr too.** `Calendar._all_meets()` is cached (was rebuilt on every call).
- **Health UI (M2 step 4):** `HealthUI` (`scripts/ui/health_ui.gd`, static helpers; `HealthUI.system()` is the health system, or null when `HealthSystem.model_enabled` is off, and then every piece shows nothing) and `HealthEventPanel` (`scripts/ui/health_event_panel.gd`). **Today card:** the top part (today / how you feel / next race) is the button for today's editor; under it WARNING SIGNS (a row per area that is at least a bit sore: word + colour `Palette.SORE_1..3`, tap = why + what helps, the one-line advice is `ui.soreness_hints` in `data/health.json`) next to INJURY & ILLNESS (`injury_block`: tier, phase, allowed, expected back, locked or "may get worse", tap = plain explanation); on a phone the injury section comes first when there is one (step 5). **Week strip:** a round "!" (colour = soreness) and a "+" (colour = tier) from the `DayInfo` fields `sore / sore_areas / health / limited / tier` (played days read the day log, today the body now). **Day editor:** `_health_box` (soreness today, INJURY LIMITS, `HealthUI.through_control` = "Train through it…" with a two-step warning then `HealthSystem.override_day`, not offered when locked; a trained-through day offers `cancel_override` = "Follow the limits again"), banned sessions greyed out in the picker as "(not with X)" (selectable as "(against limits)" once you train through), intensity above the injury's cap disabled; race day: `race_card` (can't race / racing injured, slower + may get worse) and `scratch_control` (two steps, then `Game.scratch_race(key)`, which also works on the race screen: first round only). **Stop events** of kind `diagnosis` / `sore` are drawn by `HealthEventPanel` (a diagnosis is matched to `HealthSystem.active()` by the `injury` id stored on the event); other events use the generic panel; the event card scrolls on a short window. **Training tab:** `HealthUI.plan_section(plan, week)` = load vs your normal (capped "over 300 %") and plan risk for *any* plan passed in (periodization will pass phase plans); every plan edit calls `HealthUI.refresh()` and redraws the strip and the open day. **Report:** health lines per day, one in last week's facts, `proneness_note()`. **Ctrl+S** saves (desktop: `OS.has_feature("pc")`). Button rows in narrow panels use `HealthUI._button_row()` (wraps; stacked on a phone). Checks: `health_check.gd` section "health UI (step 4)"; the tour and layout check have seeded health states (sore day, niggle, locked injury, both panels, Training/Report, race day injured) and switch the health model on for that part only.
- `Calendar` (`scripts/core/calendar.gd`): dated meets from `data/competitions.json` (keys `id@year`), eligibility, standards, date helpers (`weekday` 0 = Mon, `monday_of`, `day_type`, `format_day` → "Wed 4 Nov 2026"); `Game.entries` holds entered meet keys; `races_in_week` gives the week's race days to `WeekSim` (report `races`: `{day, meet_key, name}`). Tune with `tools/training_balance.gd` (prints a full-precision fingerprint per plan: an engine change that shouldn't change the balance must leave it identical; also rows with all days Easy / Hard).

- Races: on a race day `advance_day/advance_week` return `Game.RACE`; then `Game.race_day` (`RaceDay`: field from `Rivals`, heats/final) is run by the race screen (`scripts/ui/race_screen.gd`) and `Game.finish_race()` completes the race day. `Race` (`scripts/core/race.gd`) is the step engine (outdoor 400 m or indoor 200 m geometry); `RacePerformance` maps attributes → ability → time (`data/races.json`). Dots are drawn by `scripts/ui/race_runners_view.gd`. Tune with `tools/race_balance.gd`.
- `Rankings` (`scripts/core/rankings.gd`): season = 1 Nov–31 Oct; `season_list` ranks the player + rivals by season best (`sb`/`sb_season` on each rival). `Rivals.train_week` also lets rivals race on their own (chance per month in `data/races.json`). Career hub "Rankings" tab. Check with `tools/rankings_check.gd`.
- `SaveGame` (`scripts/core/save_game.gd`): JSON slots in `user://saves/` (autosave after every played day + snapshots from the Save button); `Game.to_dict/from_dict`. **Version 2** adds the week in progress (`WeekSim.to_dict`), last report, events, day log and system states; version-1 saves (always a Monday, no week in progress) still load. JSON makes numbers floats, so dates and counters go through `Game.int_date` / `int()`. Saves are written with full precision, and Godot's JSON reader misses the last binary digit of ~1 in 8 decimals, so `load_slot` re-reads every decimal exactly from the text (`_exact_numbers`): a loaded game continues bit for bit as without saving. Dev tools must set `SaveGame.DIR` to another folder so they never overwrite the user's saves (the tour and layout check use `user://tour_saves/`, other tools `user://tool_saves/`).
- `-s` tool scripts can't use autoload names (`Data`, `Game`) or classes that use them at compile time: `load()` those scripts inside the running tree instead.
- Visuals: the user cares about realism; get reference images/specs before drawing real-world things (stadium layout etc.) instead of guessing.

## Working rules
- **Model recommendation:** start every reply with a line saying which model the user should use for their *next* message:
  `**Next message: Opus** / **Next message: Sonnet**` (+ suggested effort: low / medium / high).
  - Opus: design discussions, architecture, complex systems, hard bugs.
  - Sonnet: routine GDScript implementation, small features, fixes.
  - Switching models mid-conversation makes the new model re-read the whole conversation (costs extra credits). So recommend a *different* model only for the start of a **new** conversation; within an ongoing one, recommend staying on the current model. When a task is finished, suggest starting a new conversation.
- Keep sessions focused on one task; record decisions in docs, not just chat.
- Commit and push at the end of every work session.
