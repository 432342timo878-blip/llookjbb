# Track & Field Career Game (Godot)

In-depth career mode track and field (yleisurheilu) game, built in Godot together with the user.

**Status:** M1 done — character creation, weekly training, season calendar, save/load, the 800m race simulation, season rankings and the responsive UI (desktop + phone portrait) are done. M2 part 1 (day-by-day mode, injuries & health; designed in GDD 4.5–4.7, steps in the roadmap): steps 1 (day engine + hooks), 2 (week strip, day editor, Today card, Report tab), 3 (health model, headless), 4 (health UI) and 5 (balance & playtest: soreness thresholds tuned, race-day "sore" bug fixed, numbers in GDD 4.6 "Tuned (step 5)") done; silent stress fractures decided and applied (option B3); step 6 (season periodization) is designed in GDD 4.8 and is built in sessions 6a–6f (roadmap): 6a (week plan storage + Easy/Normal/Hard in the plan), 6b (season model, headless: phases, targets, taper, `SeasonPlan.week_for`), 6c (race-day Form) 6d (the coach's Steady / Balanced / Ambitious plans + the ★ pick; new careers start on the ★ plan; the three missed balance targets accepted by the user, GDD 4.8 "Built (step 6d)") and 6e (season UI, GDD 4.8 "Built (step 6e)"), 6f (coach's offers, season rollover, easing back in, multi-season check, GDD 4.8 "Built (step 6f)") and the in-game help system (GDD 5 "Help") done; race realism designed (GDD 4.3.1: pack racing, rival personalities and moves, boxes and falls, pause cards + action bar, coach + TV commentary); R1 (pack engine, GDD 4.3.1 "Built (step R1)") and R2 (moves, kick chain, boxes, falls, race injuries, DNF/DQ, heats easing, race events, duel rows; GDD 4.3.1 "Built (step R2)", decisions 10–13) and R3 (player controls: event-driven cards, the action bar, Feeling word, drop to 1x, the coach's shouts; GDD 4.3.1 "Built (step R3)", decisions 14–16) done; next R4–R5 (ROADMAP "Race realism"), then the multi-year check (step 7, also seniors' race-day consistency), coaching and school. Youth opponents stay fictional (minors); real athletes only at senior level. Milestones: `docs/ROADMAP.md`.
**Design doc:** `docs/GDD.md` — the source of truth for all design decisions. Read it before design or code work.

**User:** no programming experience — explain how to run/test things in plain steps; Claude writes all code.

## Tech & structure
- Godot **4.7.2** (user's version), GDScript only, GL Compatibility renderer (PC + mobile). Base viewport 1280x720, stretch `canvas_items`/`expand`.
- `scenes/main.tscn` + `scripts/main.gd` — app shell; applies theme, hosts the current screen.
- Autoloads: `Data` (`scripts/core/data.gd`, loads `data/*.json`), `Router` (`scripts/core/router.gd`, `Router.go("screen_id")`; register screens in `SCREENS`), `Game` (`scripts/core/game.gd`, current athlete + today's date; career starts Mon 2 Nov 2026).
- `Athlete` (`scripts/core/athlete.gd`): attributes are floats 1–20 keyed by id from `data/attributes.json`; `to_dict`/`from_dict` for saving. `AthleteFactory` builds the 14-year-old from creation choices (base ranges + background answer effects from `data/background_questions.json` + 12 points, max +3 each).
- **Responsive UI:** `Layout` (`ui/layout.gd`) holds `Layout.compact` (true for a portrait/squarish window, i.e. phone). `main.gd` picks the mode on every window resize, sets the window `content_scale_size` (wide: 1280x720-based, scale floor 0.7; compact: 480 px logical width), rebuilds the theme (`ThemeBuilder.build(compact)`) and emits `Router.layout_changed`. Every screen builds its layout from `Layout.compact` and rebuilds on that signal (hub, wizard, race, load game, main menu). Rules: use `UIKit.flex()` (BoxContainer that is a row on PC, a column on phone), `Layout.page_margin()`, 44 px minimum for anything tappable, **no hover-only info** (use `UIKit.attr_row(..., description)` / `UIKit.tap_to_explain` and `ChoiceCard` instead of tooltips). Hub: tabs on top (`TabButton`) on PC, bottom bar (`BottomTabButton`) on phone. Race decisions are a full-screen dimmed overlay. Check with `tools/layout_check.gd` (live-resizes through 1280x720, 720x1280, 390x844, 1000x900, 844x390) and `screenshot_tour.gd --resolution 390x844`.
- **Backdrop:** `scripts/ui/backdrop.gd` + `ui/backdrop.gdshader` draw the background gradient; a photo in `assets/backgrounds/<screen_id>.jpg` (or `default.jpg`) is shown blurred and darkened (see the README there). Three CC BY-SA photos are included (Forss + Kuivisto at Kalevan Kisat 2018 by Tuomas Vitikainen, Lahti Stadium by Kallerna; credits in that README, still needs an in-game Credits screen). Their `.import` files must keep `mipmaps/generate=true` (the blur samples a mip level). Panels are slightly translucent (`Palette.SURFACE_PANEL`).
- **Help (GDD 5 "Help"):** texts only in `data/help.json` (`screens` + `topics`, sections ≤ ~50 words, `see` = topic links, `version`); `Help` (`scripts/ui/help.gd`: `entry / is_new / mark_seen`, "read" in `user://help_seen.cfg`, tools set `Help.SEEN_PATH`), `HelpButton` (44 px "?", "new" dot, `entry_id`), `HelpPanel` (the content, `stack` for See also / Back), `HelpOverlay.open(host, id)` (phone sheet / PC right panel over a screen). Hub: header "?" → `_help_entry()` (tab, Training page), PC = the side slot over the day editor, phone = overlay; day editor `help_requested`; race screen `_help_id()` by stage (the race waits); wizard; `HealthEventPanel.build(..., on_help)`. `Layout.stacked()` = phone or PC with the hub's side panel open (Training pages stack their rows; the hub rebuilds them when the panel opens/closes). Check: `tools/help_check.gd` (every "?" pressed, every entry used).
- Screens built in code use `UIKit` (`scripts/ui/ui_kit.gd`) helpers: labels, panels, toggles, FM-style `attr_row` with value colours.
- Screens: `scenes/screens/*.tscn` (mostly just a root node now) with scripts in `scripts/ui/`; the hub, wizard and race screen build their shell in code so it can switch layout.
- Theme is built in code: colours/sizes in `ui/palette.gd`, styles in `ui/theme_builder.gd`. Label variations: TitleLabel, HeadingLabel, MutedLabel, CaptionLabel; button variation: PrimaryButton. Font: Inter (`assets/fonts`, OFL).
- World data lives in `data/*.json` (events, attributes) — never hard-code real-world data in scripts.

- **Plan storage (M2 step 6a, GDD 4.8):** a week plan is `{"days": [7 lists of session ids], "intensity": [7 × easy/normal/hard]}` (`WeekPlan`, `scripts/core/week_plan.gd`: `make / of / days / intensity / coach / empty / copy_of / equals`; `of()` also takes the old plain Array = all Normal and leaves a week plan as it is). `Game.season` (`SeasonPlan`, `scripts/core/season_plan.gd`, `mode` repeat or phases (phases: per-season records of targets, edge shifts and edited phase weeks, built from `data/periodization.json`; new careers enter the two main championships as targets; GDD 4.8 "Built (step 6b)"; the coach's three plans are `variants` in that file, `SeasonPlan.variant(year)` / `set_variant` / `edited_phases`, a season without a record keeps the latest earlier season's plan; `SeasonPlan.coach_pick(athlete, today, health)` = the ★ (limits in `coach_pick`), `Game.start_career(a, mode, variant = "")` starts on the ★ when no variant is given, so tools in phases mode pass "balanced"; GDD 4.8 "Built (step 6d)"), `repeat_week`; in phases mode `week_for(monday)` builds `{days, intensity, why, phase, phase_week, phase_weeks, kind, target}` (phase week, ramp, lighter week, easy day before a race, taper); `week_for(monday)` is the one place that answers "what is the plan for this week") replaces `Game.training_plan`; the Training tab edits `Game.season.repeat_week` in place (Easy / Normal / Hard per day, 44 px; "Coach's plan" / "Clear week" give all-Normal plans). `WeekSim.plan` = the days, `WeekSim.plan_intensity` = the plan's intensity; `intensity(d)` = the day change, else the plan's; a change equal to the plan is dropped (`set_intensity`, `set_sessions`, and `set_plan`, which `Game.current_week()` calls every time). `Training.preview / expected_fatigue / simulate_week`, `HealthSystem.plan_risk / load_vs_normal` and `HealthUI.plan_section` take a week plan or the old Array. Injury limits and "train through it" put the *plan's* intensity back (not Normal). Tools can't name `WeekPlan` at compile time: `load("res://scripts/core/week_plan.gd").make(days, intensities)`.

- **Coach events (GDD 4.8 "Built (step 6f)"):** `SeasonSystem` (`scripts/core/season_system.gd`, id `season`; rules + texts in `data/periodization.json` `offer` / `return_block`): the "three plans" stop event (`kind` offer; `Game.start_career` on the ★, and 3 weeks before each season; answer = plan id or "later"; static `offers_enabled` for tools), the rollover on the evening before a season (★ unless chosen, targets entered), "Easing back in" (`kind` return, after 14+ days without running; `SeasonPlan.return_block`, `start_return / stop_return / return_day / return_week_on`, applied last in `week_for`, both modes). - **Form (GDD 4.8 "Form", M2 step 6c):** `FormSystem` (`scripts/core/form_system.gd`, in `Game.systems`, id `form`, no dice, `FormSystem.enabled` switch) keeps `sharpness` 0–100 (×0.93 a day + the sessions' `sharp` × intensity effect; race 15); `race_form(fatigue)` = sharpness term + freshness term as a share of race time, applied in `RaceDay._player_entrant` as time × (1 + slowdown − form) (`RaceDay.form`); `info(fatigue)` → word (Peaking / Sharp / OK / Rusty, Tired above fatigue 25), colour, text. UI: `FormUI` (`scripts/ui/form_ui.gd`): a row on the Today card (tap = explanation) and a race card in the day editor (today's race) and on the race screen. Old saves load with an empty state. `tools/form_check.gd` (ALL CHECKS PASSED, 40+ checks) also prints the calibration and the season-plan words.
- **Day engine (GDD 4.5/4.7):** `Game.date` is *today* (the next day to play); `Game.week_monday()` for week-based code (training tab, plan preview). `Game.advance_day()` plays one day, `Game.advance_week()` plays to Sunday night; both (and `finish_race()`) return `Game.DAY_DONE` / `WEEK_DONE` / `RACE` (race screen, `race_day` set) / `STOP` (unanswered stop event). A race reached during Play week continues the week after `finish_race()`; via Next day it completes just that day. `WeekSim` (`scripts/core/week_sim.gd`) is the week in progress (`Game.current_week()`, made on demand, synced with `Game.season` and entries): `play_day()` / `race_done()` per day, `end_week()` applies progression (Sunday night) → `last_report`; then `Rivals.train_week`. Day changes for this week only: `set_sessions / swap_session / skip_session / add_session / make_rest_day / set_intensity / reset_day(d, ..., by)` with `by` in player / coach / injury; only unplayed non-race days; a change equal to the plan is dropped. Intensity multipliers (load, effect) in `data/health.json` (Normal = 1.0, so the M1 balance is bit-for-bit unchanged). Day loop slots: `GameSystem` (`scripts/core/game_system.gd`) hooks `on_day_start → (training/race) → on_health → on_day_end`, `on_week_end`, `on_answer`, own `to_dict/from_dict`; `Game.systems` = `HealthSystem` (see "Health model" below) + `DevEvents` (debug builds only: **T** in the hub arms a test stop event for the end of the next played day; not an F key, since F7/F8 pause/stop a game run from the editor). Events: `Game.post_event(source, title, text, choices, stop)` → `{id, date, source, title, text, choices, stop, answer}`; `pending_event()`, `answer_event()` → the source system's `on_answer`. A stop event at day start pauses before the day is played (`week.day_started`). `Game.day_log`: per played day `{date, day_type, sessions, intensity, race, load, fatigue, events}` plus whatever systems put in `ctx.log_extra` (health: `soreness`, `health`); log and answered events keep 28 days. The hub shows a pending stop event as a dimmed full-screen panel. Check with `tools/day_engine_check.gd` (optionally `-- <v1 save file>`).

## Working rules
- **Model recommendation:** start every reply with a line saying which model the user should use for their *next* message:
  `**Next message: Opus** / **Next message: Sonnet**` (+ suggested effort: low / medium / high).
  - Opus: design discussions, architecture, complex systems, hard bugs.
  - Sonnet: routine GDScript implementation, small features, fixes.

So recommend a *different* model only for the start of a **new** conversation; within an ongoing one, recommend staying on the current model. When a task is finished, suggest starting a new conversation.
- Keep sessions focused on one task; record decisions in docs, not just chat.
- **Every new feature adds or updates its help entry** in `data/help.json` (a new screen gets a "?"; raise `version` when an entry changes meaningfully) and `tools/help_check.gd` must still pass.
- Commit and push at the end of every work session.
